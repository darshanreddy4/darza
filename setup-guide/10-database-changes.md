# 10 Changing the database safely (migrations)

Read this before you add a field, rename something, or deploy a release that changes the database. It applies the same way on your laptop, on a second laptop built from scratch, and in production.

## 1. The pieces, and where each one lives

| What | Where | Notes |
|---|---|---|
| The description of every table and column | `apps/api/prisma/schema.prisma` | You edit this |
| The steps that build or change the tables | `apps/api/prisma/migrations/<timestamp>_<name>/migration.sql` | Generated by Prisma, kept in git, one folder per change |
| The record of which steps have already run, with a checksum of each file | A table named `_prisma_migrations` inside the database | Created by Prisma. Never edit by hand unless this guide says so |
| Your actual data | PostgreSQL (the `pgdata` Docker volume in development, the `deploy` volume or your managed database in production) | Prisma never stores data itself |

The migration files travel with the code (git). The database remembers what it has already applied. Starting the API in production applies only the steps the database has not seen yet.

## 2. The two commands that matter

| Command | Use it for | What it does | Can it erase data? |
|---|---|---|---|
| `npx prisma migrate dev --name what_changed` | **Your laptop only** | Creates a new migration from your schema edit and applies it. Applies any new migrations pulled from git | Yes, if it finds drift it offers to reset the database (it asks first) |
| `npx prisma migrate deploy` | **Production, staging, CI, and any server** | Applies migrations that have not run yet, nothing else | No. It never resets and never drops the database |

The Docker image runs `migrate deploy` by itself every time the API starts (turn this off with `RUN_MIGRATIONS=false`). You do not run it by hand in production.

Never run `migrate dev`, `migrate reset` or `db push` against a production database.

## 3. The normal workflow for a database change

Do these on your laptop, in order.

1. **Make sure your database is current.** In `apps/api`: `npx prisma migrate status` should say "Database schema is up to date".
2. **Edit `apps/api/prisma/schema.prisma`.** For example add `nickname String?` to a model.
3. **Create the migration:**
   ```bash
   cd apps/api
   npx prisma migrate dev --name add_user_nickname
   ```
   Use a short name that says what changed (`add_user_nickname`, `drop_old_banner_field`). This writes a new folder under `prisma/migrations/`, runs it on your laptop database, and refreshes the Prisma client.
4. **Read the generated `migration.sql`.** This is the most important step.
   - It must not be empty.
   - Look for `DROP TABLE`, `DROP COLUMN`, `ALTER COLUMN ... TYPE` and `SET NOT NULL`. Those can lose or reject data (see section 5).
   - Add data fixes if needed (section 6).
5. **Update the code** that uses the new field, and the tests.
6. **Run the checks:** `cd apps/api && npx tsc --noEmit && npm test`, and the browser tests (they build a fresh database from all migrations with `migrate deploy`, so they prove the whole chain works).
7. **Commit the schema and the new migration folder together.** A migration that is not committed will not reach production.

If you cannot answer a prompt from `migrate dev` (for example when scripting), create the SQL without applying it:

```bash
npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script > prisma/migrations/<timestamp>_<name>/migration.sql
npx prisma migrate deploy && npx prisma generate
```

Check the file is not empty before applying it.

## 4. Rules to keep in mind

1. **Never edit a migration that has already been applied anywhere.** Write a new migration instead. Editing an old file makes `migrate dev` think the database is out of step and offer to reset it.
2. **Never delete or rename a migration folder.** The folder names are the history, and they run in timestamp order.
3. **Never change a database by hand** (a manual `ALTER TABLE`) without also putting it in a migration. Otherwise laptops, staging and production drift apart.
4. **Commit `schema.prisma` and `migrations/` together.**
5. **Keep Prisma's version the same** on every laptop and in the Docker image (`apps/api/package-lock.json` fixes it for laptops, and the API `Dockerfile` installs the same version for the migration command).
6. **Always take a backup before a production release** that includes a migration (`deploy/backup.sh`, section 8).
7. **Keep each migration small and focused.** One idea per migration is easier to review and to fix.

## 5. Safe changes and risky changes

| Change | Risk | How to do it |
|---|---|---|
| Add a new table | Low | Just do it |
| Add a nullable column, or a column with a default | Low | Just do it |
| Add an index | Low on small tables. On a large table it can lock writes while it builds | Do it at a quiet time |
| Add a required (`NOT NULL`) column with no default | **Fails if the table already has rows** | Add it with a default, or add it nullable, fill it, then make it required in a later migration |
| Rename a column or table | **Prisma writes it as drop and create: data is lost** | Edit the generated SQL to use `ALTER TABLE ... RENAME COLUMN ...`, or use the two-step method below |
| Drop a column or table | **Data is lost for good** | Only after the code no longer uses it, and after a backup |
| Change a column's type | Can fail or lose values | Add a new column, copy the data across with `UPDATE`, switch the code, drop the old one later |
| Add a unique constraint | Fails if existing rows already contain duplicates | Clean the duplicates first, in the same migration |

**The two-release method for anything risky:**

1. Release 1: add the new column, copy the data, and change the code to use the new column (the old one still exists, so rolling back the code is safe).
2. Release 2 (days later, once all is well): drop the old column.

This also keeps a release safe while old and new copies of the API run at the same moment during a deploy: the database change must work with **both** the old and the new code.

## 6. Putting data changes inside a migration

A migration is plain SQL, so it can also fix data. The migration `20261013185013_brand_everywhere` is an example: it replaced the old brand name in existing texts with `{brand}`. Rules for this:

- Keep the data fix in the **same** migration as the structure change that needs it, so it cannot be forgotten.
- Make it safe to run once on a database that already has the right values.
- Never put test or sample data in a migration. Sample data belongs in the seed script, which production does not use.

## 7. Setting up on another laptop, or from scratch

1. Install what is listed in [01-requirements.md](01-requirements.md), then `git clone` the project.
2. Start the helpers: `docker compose up -d` in the project folder.
3. In `apps/api`:
   ```bash
   cp .env.example .env
   npm install
   npx prisma migrate dev     # builds every table from the migration files
   npm run db:seed            # sample admin and sample products (development only)
   npm run dev
   ```
   On a brand-new empty database, `migrate dev` and `migrate deploy` give the same result: all migrations run in order.
4. In `apps/web`: `cp .env.example .env.local && npm install && npm run dev`.

After every `git pull` that brings new migration folders, run `npx prisma migrate dev` once in `apps/api`.

To copy real data to another machine instead, use a database backup: `deploy/backup.sh` there, then `deploy/restore.sh <file>` on the other machine.

## 8. The production release routine

Use this every time a release contains a migration. For a release with no migration, the same steps work and the migration step simply does nothing.

1. **Test** on your laptop and in CI (the browser tests build a fresh database from all migrations).
2. **Back up production:** `cd deploy && ./backup.sh`, then copy the file off the server. For a managed database, take a snapshot.
3. **Deploy:** `git pull && docker compose up -d --build` (or deploy the new images on your platform). The API container runs `prisma migrate deploy` before it starts serving.
4. **Check:** `docker compose logs api` shows the migrations applied; `https://api.yourshop.com/health/ready` returns `"status":"ok"`; place a test order and open the admin.
5. **Keep the backup** for at least a few days.

If you run several copies of the API, run migrations from one place only: set `RUN_MIGRATIONS=false` on the copies and run one `npx prisma migrate deploy` as a single job before the release. (Prisma uses a database lock, so simultaneous runs do not corrupt anything, but one job is cleaner.)

To see where a database stands, in the API container or in `apps/api` with `DATABASE_URL` set:

```bash
npx prisma migrate status
```

In the Docker setup: `docker compose run --rm api npx prisma migrate status`.

## 9. When something goes wrong

| Symptom | Cause and fix |
|---|---|
| `migrate dev` says a migration "was modified after it was applied" and offers to reset | An applied file was edited. If you only changed it by mistake, restore the file from git. If the change was intentional (for example a rename), update the stored checksum: compute `shasum -a 256 prisma/migrations/<folder>/migration.sql` and run `update _prisma_migrations set checksum='<value>' where migration_name='<folder>'` on that database. Do this on every database that already applied it. In a disposable dev database you can instead answer yes to the reset |
| `migrate dev` says the database has "drifted" | Someone changed the database by hand, or you are on a different branch. On your laptop you may reset. **In production never reset; restore from backup or write a corrective migration** |
| A migration fails during a production deploy | Prisma stops and reports the failing step; the API will not start. Read the error. Then either fix the data and mark it with `npx prisma migrate resolve --applied <name>` (if you finished the step by hand) or `--rolled-back <name>` (if you undid it) and deploy again. If data was damaged, restore the backup |
| `Error: P3009` or "failed migrations found" | A previous attempt failed halfway. Use `migrate resolve` as above, then deploy again |
| Errors about missing columns after a `git pull` | You have not applied the new migrations: `npx prisma migrate dev` |
| The API starts but behaves oddly after a schema change | The Prisma client is out of date: `npx prisma generate` and restart (the Docker image does this when it builds) |
| `migrate deploy` hangs | Another run holds the lock. Wait for it, or check for a stuck connection in the database |

## 10. One-page checklist before you ship a database change

- [ ] I created the change with `migrate dev --name ...` (not by hand-editing the database)
- [ ] I read the generated SQL: no surprise `DROP`, no rename written as drop and create
- [ ] It works on a database that already has rows (new required columns have a default)
- [ ] The code works with both the old and the new database structure (safe during a deploy)
- [ ] Unit tests and browser tests pass
- [ ] The schema file and the new migration folder are committed together
- [ ] I took a backup of production before deploying
- [ ] After deploying I checked `/health/ready` and tried an order and the admin
